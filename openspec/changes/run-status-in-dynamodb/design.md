# Design

## Context

See `proposal.md` for the motivation. Facts that shape the design, checked against `main` at
`acbbd1f`. `assumptions.md` has line references.

- Status today is one S3 object written by user-data (`aws s3 cp - …/run-status`) and polled with
  `GetObject` by the launching CLI only. A run whose instance ends without that object is reported
  as vanished.
- User-data is generated by the CLI for each run, and the AMI contains none. The status writer and
  the status poller therefore always come from the same CLI build.
- `RunInstances` applies the `baas-request-id=<runId>` tag in the same call that creates the
  instance (`tagSpecifications`). An instance never exists without that tag.
- `baas run` validates the project against `[A-Za-z0-9._-]+` before the clock read, the upload and
  the launch.
- **Readers of the results table:**
  - two Scans (`--all-projects` and the project picker). The picker builds its list from the
    `project` attribute, not from `pk`.
  - two `requestId-index` queries (`queryByRequestId` and `resultPathForRun`, which reads the first
    row it finds).
- **Current DynamoDB rights:**
  - `RunnerRole`: `PutItem` and `BatchWriteItem`.
  - `OperatorRole`: `Query`, `Scan` and `GetItem`. The main spec says only `Query`/`GetItem`; this
    change's delta corrects that drift.
  - The deployer policy: no item-level action at all.

## Goals / Non-Goals

**Goals:**
- Status that any operator can read, kept in a place a single query lists.
- A complete record from before the launch until the end, including runs that never launched or
  never reported.
- No change to what a stored measurement means.

**Non-Goals:**
- Reattaching a new `baas run` process to a detached run (`--detach`/`attach`, rejected in the
  usage analysis §5).
- Backfilling run items for past runs.
- `baas runs show` and `baas runs diff`, which belong to the queued `runs-command` change. This
  change only creates the `runs` group they join.
- Any change to the three termination layers beyond the watchdog's one extra status write.

## Decisions

### Run items share the results table, in one `RUN` partition

`pk = RUN`, `sk = <createdAt>#<runId>`, `gsi1pk = <runId>`, `gsi1sk = RUN`.

The one-partition shape was chosen because U3's questions are installation-wide. Teardown has no
project, and "what is running?" spans every project. One partition answers both with one `Query`,
newest first. The write rate is a handful of runs a day, far below a single partition's limits.

`gsi1sk = RUN` cannot collide with any measurement:
- a measurement's index sort key starts with a fully qualified class name or with `JCSTRESS#`;
- either way it never equals the bare string `RUN`.

So a `requestId-index` query can address the run item exactly with `gsi1sk = RUN`, rather than
depending on sort order. Keys are added to `ResultKeys`; the item is built and read by a new
run-item mapper beside `MeasurementItemMapper` in `baas-model`. This is the same "constructed in one
place" rule as for measurement keys.

*Rejected:*
- **`RUN#<project>`, the first decision.** Listing across projects would need a Scan to discover
  the projects first, and teardown could not use it at all.
- **A separate `-runs` table.** It is another retained resource, and it needs a deployer-policy
  edit in a policy that is already close to its size budget.

### Run items are excluded from measurement readers by key, and rejected by the mapper

- Both Scans gain `begins_with(pk, :resultPrefix)` with `RESULT#`.
- `queryByRequestId` gains a sort-key condition that excludes `RUN`.
- `MeasurementItemMapper.fromItem` throws on any item whose `pk` is not `RESULT#…`.

A filter that a future reader forgets then fails loudly instead of rendering an empty row or
offering a phantom project in the picker.

`resultPathForRun` queries `gsi1pk = <runId> AND gsi1sk = RUN` first. If that finds nothing, it
falls back to today's first-measurement lookup, which is how runs recorded before this change keep
resolving.

*Rejected:* tagging run items with `exclude_from_results=true` to reuse the existing exclusion
filter. That flag means "keep these measurements out of comparisons", so overloading it would hide
runs from `--all-runs` semantics they have nothing to do with. It would also leave
`MeasurementItemMapper` able to misread a run item.

### Every write is one conditional `UpdateItem`, and the first terminal status wins

Each writer sets `status`, `updatedAt` and its own fields. The identity fields (`runId`,
`project`, `createdAt`, `resultPath`, `instanceType`, `tags`, and `instanceId` once known) are set
with `if_not_exists`, so whichever write arrives first creates a complete item. The values are the
same on both sides: the CLI put them into user-data, and the instance id comes from EC2 either way.

The condition is:

```
attribute_not_exists(#status)
  OR NOT (#status IN (:completed, :timedOut, :cancelled, :launchFailed)
          OR begins_with(#status, :failedPrefix))
```

`failed:<n>` is matched by prefix, so exit codes need no enumeration.

*Rejected:* letting the instance's outcome override `cancelled`. It would need a two-branch
condition and an asymmetry the spec has to explain, only to make a label more accurate. The
measurements are stored either way.

### The CLI reserves the run before launching it

The order in `RunCommand` becomes:

```
preflight (project, table, JAR, image) → name the run (one clock read) → upload
→ resolve networking → UpdateItem launching ──fail──▶ exit ≠ 0, nothing launched
→ RunInstances ──ok──▶ UpdateItem launched (+instanceId) → shutdown hook → poll
             └─fail─▶ UpdateItem launch-failed (+error code) and PutObject launch-error.txt
                      (each best effort) → report the original error → exit ≠ 0
```

A failed reservation stops the launch because an instance without a record is exactly the
invisibility U3 removes. It also follows the CLI's rule of detecting every failure it can before
money is spent.

*Rejected:*
- **Writing only after `RunInstances`.** It leaves a failed launch unrecorded, so
  `baas download <runId>` has nothing to resolve.
- **An age-based timeout for a stale `launching` item.** Not needed: the `baas-request-id` tag
  answers the question exactly.

### `vanished` is computed when reading, from one tag-filtered `DescribeInstances`

A non-terminal item is resolved against EC2:
- with its `instanceId` when the item has one;
- otherwise with `tag:baas-request-id`.

`baas runs list` collects every non-terminal row's run id into a single `DescribeInstances` call
filtered on that tag (up to 200 values per filter). The instance's state decides: `pending` or
`running` means in flight, and anything else, including no instance, means vanished. The result is
never written back. Writing it back would make a list command a writer and would race an instance
that is only slow to report.

### User-data writes status through one shell function, with no fallback

`run_status <status>` wraps `aws dynamodb update-item` with the condition above.
- **Quoting.** Every value it puts into JSON is already constrained: the run id has a fixed format,
  the project matches the PR #73 regex, the status comes from a fixed set, and the instance id
  comes from IMDS. Following the quoting invariant, they are still captured into variables first,
  and the `--key` and `--expression-attribute-values` JSON contains only `${VAR}` references.
- **Retries.** The call runs with `AWS_RETRY_MODE=standard` and a raised `AWS_MAX_ATTEMPTS`.
- **A refused condition.** `ConditionalCheckFailedException`, found in stderr, is logged as
  "status already terminal" and returns success.
- **Any other failure** is logged and also returns. Because nothing aborts the script, the boot-log
  upload and the termination that follow always run.

Placement:

```
INSTANCE_ID → watchdog started → run_status running   (invariant: nothing before the watchdog)
… manifest, JAR fetch, java -jar …
run_status completed|failed:<n>  (replaces the S3 sentinel) → boot log → terminate
watchdog subshell: run_status timed-out → boot log → terminate
```

*Rejected:* falling back to the S3 sentinel when the DynamoDB write fails. That keeps two sources
of truth and two poll paths in order to cover a failure the CLI can already report honestly (next
decision).

### A lost terminal write is reported from the measurements, not guessed

When the poll sees a non-terminal item and a terminated instance, it re-reads once, keeping today's
check for a status written just before termination. It then calls `queryByRequestId`, which already
runs for the summary.
- If measurements exist: "results stored; the instance's final status was lost", exit 1. The
  benchmark's exit code is unknown, so success is not claimed.
- If none exist: the vanished report, naming the boot log.

### `--no-database` is removed from both the CLI and the runner

A run with no table has nowhere to record its status, and the flag dates from before the CLI. A run
that can launch always has an installation and therefore a table. The bucket, the AMI pointer and
the networking are all derived from the prefix.

- The runner's exactly-one-of check shrinks to `--results-table` or `--mongo-connection-string`.
- `NoOpResultsStore` is deleted.
- No integration test depends on it: the service ITs construct a `MongoResultsStore` directly, and
  the contract suite runs against LocalStack.
- User-data always passes the table name.

Taking the MongoDB adapter out of the runner was not considered here. Its retirement is a separate
open decision recorded in *Accepted risks*.

### Teardown keeps its EC2 gate and reads run ids from instance tags

The deployer policy grants no `Query` or `GetItem` on the table. Adding them would spend characters
from a policy close to its inline budget, in order to learn something the instances already say:
- `listRunningBenchmarkInstances` returns its instances' tags alongside their ids;
- the message names each run id, instance and state, and points to `baas runs terminate <runId>`.

An admin with deployer credentials only will be pointed at an operator command. This is accepted:
operating runs is the operator's job.

### `baas runs` is a group of subcommands; `terminate` shares the shutdown hook's code

`list` and `terminate` are subcommands, and a bare `baas runs` prints usage. This matches every
other group (`admin`, `config`) and keeps a destructive action away from read-only filter options.

`terminate` and `RunCommand`'s shutdown hook call one method:
1. record `cancelled`, conditionally;
2. terminate the instance.

`OperatorRole` already holds tag-scoped `ec2:TerminateInstances`. Confirmation follows teardown's
pattern: prompt on an interactive terminal, `--yes` to skip, and refuse without a terminal.

`list` reuses `baas results`' output plumbing: `Console`, `console.Table`, and JSON/CSV under
`Locale.ROOT`.

### IAM uses `dynamodb:LeadingKeys` in both directions

- **RunnerRole:**
  - `PutItem` and `BatchWriteItem` with `ForAllValues:StringLike dynamodb:LeadingKeys = RESULT#*`;
  - `UpdateItem` with `ForAllValues:StringEquals dynamodb:LeadingKeys = RUN`.
- **OperatorRole:** `UpdateItem` with the same `RUN` condition.
- The deployer policy is unchanged.

`infra/operator-policy.json` is the reference copy that `Operator policy reference copy stays in
sync` pins, and it changes in step with the template.

## Comparability

- **No change to what a stored measurement means.** The measurement items, their keys, their tags
  and the runner's measurement path are unchanged.
- **User-data gains one `aws dynamodb update-item` call (`running`) before the benchmark starts**,
  at the same point in the script as the environment-manifest uploads. It completes before the JVM
  starts, so it cannot overlap a measurement.
- **The final status write replaces an `aws s3 cp` at the same point, after the benchmark exits.**
- **The watchdog's write happens only on the kill path.**

Results recorded before and after this change are therefore directly comparable.

## Risks / Trade-offs

- **[A new CLI against a stack that hasn't been updated]** The `launching` write is denied because
  the operator role has no `UpdateItem` yet, so every run is refused.
  → Fails safe, with no instance launched. The error names `baas admin setup` as the fix, and the
  migration plan says to update the stack first.
- **[An old CLI against an updated stack]** Unaffected. It writes and polls the S3 sentinel, and
  the runner's narrowed `PutItem` still covers `RESULT#`.
- **[`ForAllValues` passes vacuously when the request carries no leading key]** Every
  `PutItem`/`BatchWriteItem`/`UpdateItem` request carries its key, so the condition always has
  values to test.
  → A template test pins both conditions, and the integration scenario "the runner cannot put
  items outside the measurement partitions" covers the deny.
- **[Instance status writes can be lost for good]** For example, when DynamoDB is unreachable from
  the instance.
  → The CLI reports that results were stored and the final status was lost, from the measurements.
  `baas runs list` shows such a run as vanished once the instance is gone.
- **[The `RUN` partition grows without bound]** About 3 KB per run, and no TTL by design: the table
  declares none, and history is retained.
  → At 10,000 runs the default listing still reads the partition newest-first and stops at the
  limit. Only `--in-flight` and `--tag` read further. This is acceptable at the expected volume.
- **[`--no-database` removal breaks a standalone runner user]** The runner can no longer run with
  no store at all; LocalStack becomes the minimum. No such user is known (*Accepted risks*,
  MongoDB row).
  → Stated in the proposal as **BREAKING**.

## Migration Plan

1. Update the stack first with `baas admin setup` from the new CLI. This adds the IAM grants and
   narrows `PutItem`. Old CLIs keep working against it.
2. Use the new CLI for runs. There is no data migration and no backfill. Old `run-status` objects
   stay in S3 as artifacts, and old runs still resolve through their measurements.
3. Rollback: the old CLI works against the updated stack (see Risks). Run items written in the
   meantime are inert to it, because every reader filters by `RESULT#` or never reaches `RUN`.

## Resolved Questions

- **Keep the S3 sentinel for version skew?** No. The CLI generates user-data per run, so the writer
  and the poller are always the same build (`RunCommand` → `UserDataScriptBuilder.build`). The AMI
  only needs the `aws` CLI, which it already has.
- **The run item of a run with an invalid project?** It cannot exist.
  `RunCommand.requireValidProject` rejects the name before the clock read, the upload and the
  launch, and the reservation is written after all three.
- **Which terminal status wins?** The first one written (decided during explore).
- **Does `--no-database` keep a status path?** No: the flag is removed (decided during explore).

## Open Questions

- The exact `AWS_MAX_ATTEMPTS` for the status call (for example 8). It is tuning that changes no
  spec or task.
- Whether `baas run`'s status line shows the item's status (`launched`, `running`) instead of the
  EC2 state. It is cosmetic and can follow later.
