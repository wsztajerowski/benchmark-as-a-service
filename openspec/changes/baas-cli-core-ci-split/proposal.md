## Why

`baas-cli`'s `SetupCommand`/`TeardownCommand` currently provision a single CloudFormation stack that mixes infrastructure the self-installed local CLI needs (VPC, S3 bucket, `RunnerRole`) with infrastructure that only the GitHub Actions CI path needs (OIDC provider, `WorkflowRole`, GitHub org/repo/workflow parameters). That means the local `baas` binary — running with a developer's own AWS credentials — touches resources and parameters tied to GitHub API/OIDC trust, which shouldn't be within reach of a locally-run tool. Uncommitted work-in-progress (`infra/cf-template-core.yaml`, `infra/cf-template-ci.yaml`, `infra/deployer-policy.json`) already points at splitting these concerns into two independent stacks; this change formalizes that split, wires it into `baas-cli`, and fixes inconsistencies found in the WIP templates (e.g. a bucket-name mismatch between `S3MainBucket` and `RunnerRole`'s S3 policy).

## What Changes

- **BREAKING**: `baas setup`/`baas teardown` move under a new `baas admin` subcommand group (`baas admin setup`, `baas admin teardown`), signaling they require the elevated deployer IAM policy.
- **BREAKING**: `baas admin setup` no longer creates, updates, or reads any GitHub/OIDC-related resources. All of `--github-org`, `--github-repo`, `--workflow-id`, `--workflow-branch`, `--oidc-provider-arn` are removed from `SetupCommand`. The GitHub OIDC provider + `WorkflowRole` move to a separate `cf-template-ci.yaml` stack that `baas-cli` never creates, reads, or deletes — it is deployed/torn down manually (`aws cloudformation deploy`) by whoever operates GHA CI.
- `SetupCommand.loadTemplate()` reads the classpath resource `/templates/cf-template-core.yaml`. `infra/cf-template-core.yaml` is the single source of truth: `baas-cli/pom.xml` copies it into the JAR at `templates/` at build time (no duplicated copy under `src/main/resources/`). Only the core template is bundled into the `baas-cli` JAR; `cf-template-ci.yaml` and `deployer-policy.json` live only under `infra/`.
- Fix the bucket-name mismatch in `cf-template-core.yaml`: `RunnerRole`'s S3 policy is corrected to reference `baas-${ResourceNamePrefix}` (matching the actual `S3MainBucket` resource name), instead of the stale `${ResourceNamePrefix}-main`.
- `~/.baas/config.yaml`: `aws.stackName` (default `"baas-main"`) is renamed to `aws.coreStackName`. `baas admin setup` always sets it to `baas-<prefix>` (the prefix is derived from the caller's AWS identity — see below); the static default is only a placeholder.
- `TeardownCommand` drops its OIDC-provider-retained message; teardown safety gates (no active runs, explicit confirmation, opt-in `--delete-bucket`, MongoDB never touched) are otherwise unchanged.
- Two distinct IAM identities cover the two privilege levels: `BaasCliOperatorRole` (narrow, standing — an `AWS::IAM::Role` created automatically by the core stack itself, assumed via `sts:AssumeRole` by whoever runs `baas run`/`baas results`/`baas config` — covers ec2:RunInstances, tag-scoped terminate, SSM mongo path + AMI-lookup path, S3 bucket object access, `iam:PassRole` on `RunnerRole` only; trust scoped to the account root, so no stack parameter is needed to name the operator) and `BaasCliDeployerPolicy` (elevated, created manually before the stack exists — matches `infra/deployer-policy.json`: CloudFormation stack lifecycle including delete, VPC/EC2 networking create/delete/describe, IAM role/instance-profile create, S3 bucket create).
- `baas admin setup` remains self-sufficient: it accepts `--region`/`--aws-profile`/`--mongo-uri` directly, **derives the resource prefix deterministically from the caller's AWS identity (ARN)** rather than taking a `--prefix` flag, applies defaults, deploys the core stack, and writes `config.yaml` as a side effect. No required prior `baas config set` step. Installing the `baas` binary and running `baas admin setup` remain two separate, deliberate actions (an install script never runs `admin setup` automatically).
- Everything else (public-subnet outbound-only networking, MongoDB connect-only via SSM SecureString, 3-layer EC2 timeout/watchdog, `benchmark-runner.jar` delivery from GitHub Releases with `--runner-jar` override, `run`/`results` behavior) is unchanged.

## Capabilities

### New Capabilities
- `core-stack-provisioning`: Requirements for `baas admin setup`/`baas admin teardown` — what the core CloudFormation stack contains (VPC/subnet/IGW/S3-gateway-endpoint/SG/S3-bucket/RunnerRole/OperatorRole), what it explicitly excludes (no GitHub/OIDC resources), the operator/deployer IAM identity model (an auto-created, assumable `OperatorRole` vs. an out-of-band `BaasCliDeployerPolicy`), config.yaml fields it writes, and teardown safety gates.
- `cli-command-structure`: Requirements for the `baas` command tree grouping — `admin` subcommand group for deployer-privileged commands (`setup`, `teardown`) vs. top-level daily-use commands (`run`, `results`, `config`).

### Modified Capabilities
(none — no pre-existing `openspec/specs/` entries; this is the first OpenSpec change for this repo)

## Impact

- **Code**: `commands/SetupCommand.java`, `TeardownCommand.java` (move under `commands/admin/`; drop the GitHub/OIDC options — already removed from `SetupCommand` — and Teardown's OIDC-retained message; `SetupCommand` also prints the new `OperatorRoleArn` stack output with assume-role setup instructions), `BaasApp.java` (register the new `admin` subcommand group), `config/BaasConfig.java` (rename `stackName` → `coreStackName`), and the remaining `stackName` call sites in `commands/ConfigSetSubcommand.java` and `commands/ConfigShowSubcommand.java`.
- **Resources**: `baas-cli/src/main/resources/templates/cf-template-main.yaml` removed; the core template is sourced directly from `infra/cf-template-core.yaml`, which `baas-cli/pom.xml` copies into the JAR at `templates/` (single source of truth, no duplicated copy).
- **Infra**: `infra/cf-template-core.yaml` (bucket-policy fix, plus a new `OperatorRole` resource and `OperatorRoleArn` output), `infra/cf-template-ci.yaml`, `infra/deployer-policy.json` (missing `cloudformation:DeleteStack`/`ec2:DescribeInstances`/`ssm:DeleteParameter` actions added — discovered via manual verification of the teardown safety gates against a real scratch account), `infra/operator-policy.json` (new — static reference copy of `OperatorRole`'s permission statements, for review or manual role creation before a core stack exists).
- **Docs**: `docs/redesign.md` / `docs/aws-migration-plan.md` become superseded by this OpenSpec change for the setup/teardown/command-structure areas they cover; `infra/README.md` updated to describe the two-stack deploy procedure and the operator-role assume-role setup flow.
- **No changes** to `benchmark-runner` module, GHA workflow YAML files, `RunCommand`/`ResultsCommand`/`ConfigSetSubcommand`/`ConfigShowSubcommand` behavior, or MongoDB/networking design.
