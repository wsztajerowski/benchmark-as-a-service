# CLI architecture styles — survey and fit for BaaS

Date: 2026-10-13. Scope: architecture styles used for command-line applications, compared against
`benchmark-as-a-service` (BaaS) to choose a target for a boundary refactor. Constraint: stay on
Java 21+, picocli, Maven, AWS SDK v2; modules and packages may change.

### Observed style

A **hybrid of flat command-centric and loose layering, with islands of ports-and-adapters**:

- **Commands own orchestration.** `RunCommand` (927 lines) builds clients from `AwsClientFactory`,
  `new`s each infra service inline, sequences reserve → upload → user-data → launch → poll →
  report, and owns the shutdown hook. `SetupCommand` (627 lines) does the same for the stack. Only
  these two command classes import the AWS SDK directly; the rest go through `infra`/`jobs`/`results`.
- **Manual wiring through a factory.** `AwsClientFactory` (deferred region and credentials) plays
  the role of gh's `cmdutil.Factory`: every client a command needs, built lazily. `BaasApp.configService(spec)`
  is the other wiring point. No DI container.
- **Ports exist where a hard test needed one.** `JobSession` is written against `JobRecorder` and
  `JobSession.Instances`; `JobsShowSubcommand.Sources`; `Supplier<String> answerReader` for prompts.
  Elsewhere, tests fake the **AWS SDK client interfaces themselves** (`FakeEc2 implements Ec2Client`,
  `FakeImageBuilder`, `FakeSsm`) — no Mockito in the build — and LocalStack covers S3/DynamoDB (`*IT`).
- **Pure logic is already extracted in places** (`ResultsFilters`, `ResultsGrouping`, `PackagesDiff`,
  `JobListing`, the renderers, `DeploymentNameRule`) — the functional-core instinct is present but
  not a rule.
- **The shared contract is a module** (`baas-model`) owning keys (`ResultKeys`), layout (`JobLayout`,
  `JobId`), vocabulary (`TagKeys`, `JobStatus`) and DynamoDB item mapping. This is the strongest
  boundary in the system and is enforced by the build.
- **`infra` is a type-named bucket**: it mixes AWS adapters, pure renderers of templates/scripts and
  deployment policy (`OperatorSession`), so the package says "touches the outside world, probably"
  rather than anything precise.

What a boundary refactor would address: orchestration inside picocli classes (untestable `call()`
success path — CLAUDE.md says no JVM test executes `RunCommand.call()`'s success path), a catch-all
`infra` package, and the bash user-data runtime's contract with `baas-model` being implicit
(strings exported from `DynamoDbJobRecorder` rather than from the model).

## 2. The styles

Each entry: core idea, typical layout, testing, strengths, weaknesses, when it fits, exemplars,
then **fit for BaaS**, a **BaaS sketch**, and **migration cost**.

### 2.1 Flat command-centric ("script with a parser")

**Core idea.** Each command class parses its options and does the work inline. Shared helpers grow
in a `util` package. The parser framework is the architecture.

**Layout.** `cli/Main`, `cli/commands/*Command`, `cli/util/*`.

**Testing.** End-to-end through the parser (`new CommandLine(app).execute(args)`) with captured
stdout; external systems faked at the client/HTTP layer or not at all.

**Strengths.** Zero ceremony; one file tells the whole story; fastest to write.
**Weaknesses.** Logic is welded to the parser lifecycle (picocli instantiates commands, injects
fields, calls `call()`); reuse across commands means static helpers; testing a business rule means
driving the parser and faking every client the command happens to touch. Degrades past a few
thousand lines or a second external system.
**Fits.** < ~2k lines, one external system, one runtime, short-lived tools.
**Exemplars.** Most picocli/Click/Cobra quick-start CLIs; JBang's `init --template=cli` output;
small single-file `jbang` scripts.

**Fit for BaaS.** Poor, and BaaS has already left it — but `RunCommand`/`SetupCommand` are its
remnants. 8 AWS services and three runtimes are far past where it holds.
**Sketch.** Today's tree with `jobs`/`results`/`infra` folded back into commands. Not a target.
**Migration cost.** Negative direction; n/a.

### 2.2 Layered (presentation / service / data access)

**Core idea.** Horizontal layers with downward-only dependencies: commands (presentation) → services
(application/business) → repositories/clients (data access). Fowler's *PresentationDomainDataLayering*.

**Layout.** `cli/commands`, `service/*Service`, `repository/*Repository` or `aws/*Client`, `model/`.

**Testing.** Commands tested with services stubbed; services tested with repositories stubbed
(commonly Mockito); repositories tested against LocalStack/Testcontainers.

**Strengths.** Universally understood; easy to enforce with ArchUnit or modules; separates parser
from logic.
**Weaknesses.** Organised by technical role, so one feature is spread over three packages; services
tend to depend on concrete data-access classes (dependency points *down* at AWS, not *in* at the
domain), so a service test still needs AWS-shaped fakes; layers invite pass-through methods.
**Fits.** Medium codebases with one dominant store and many CRUD-like commands.
**Exemplars.** Spring Shell sample apps; the classic Spring "controller/service/repository" shape
re-used under picocli.

**Fit for BaaS.** Moderate. BaaS is not CRUD: its hard parts are cross-service sequences with
ordering invariants (repoint SSM before deregistering the AMI; record status before terminate;
register shutdown hook before `RunInstances`). Layering would put those sequences in services —
good — but the services would depend on concrete AWS services, which is where BaaS's tests already
hurt.
**Sketch.**
```
baas-model            (unchanged)
benchmark-runner      (unchanged)
baas-cli
  pl.wsztajerowski.baas.cli        picocli commands, Console, LoggingMixin
  pl.wsztajerowski.baas.service    RunService, SetupService, TeardownService, ImageService, ResultsService, JobsService
  pl.wsztajerowski.baas.aws        Ec2*, S3*, Dynamo*, CloudFormation*, ImageBuilder*, Ssm*, Sts/OperatorSession, AwsClientFactory
  pl.wsztajerowski.baas.render     UserData, RunnerImage, DeployerPolicy renderers
  pl.wsztajerowski.baas.config
```
**Migration cost.** Low–medium: mostly moving `RunCommand`/`SetupCommand` bodies into services and
renaming `infra` → `aws` + `render`. Does not by itself fix test seams.

### 2.3 Hexagonal / ports & adapters (and Clean / Onion)

**Core idea.** Cockburn: the application core talks to the world only through *ports*
(purpose-named interfaces it owns); *adapters* implement them for a technology. Driving adapters
(the CLI, a test harness) call in; driven adapters (AWS) are called out. Clean Architecture and
Onion add concentric rings (entities → use cases → interface adapters → frameworks) with the
dependency rule pointing inward.

**Layout.** `domain/`, `application/` (use cases + port interfaces), `adapters/in/cli`,
`adapters/out/aws/{ec2,s3,dynamo,…}`; often one Maven module per ring.

**Testing.** The core is tested with in-memory port implementations (hand-written fakes, not
SDK fakes); each adapter has its own contract/integration test against LocalStack or the real
service; the CLI adapter tested by parser-level tests with the core stubbed.

**Strengths.** The clearest boundary of any style; replaces "fake an `Ec2Client` with 200 methods"
with "fake `Instances` with 3"; a new runtime or front end (e.g. a future service, a GitHub Action)
plugs in as another driving adapter.
**Weaknesses.** Ceremony: a port + adapter + DTO per external interaction; mapping between domain
and SDK types; risk of "interface for everything" and anaemic pass-through ports; Clean's ring
modules are heavy for one maintainer. Ports designed up front tend to be wrong; harvested from real
tests they tend to be right.
**Fits.** Many external systems, long-lived logic with invariants worth testing in isolation, or
multiple front ends.
**Exemplars.** No major CLI uses it textbook-style; Terraform's `backend.Backend` /
`backendrun.OperationsBackend` is a real driven port (local vs remote/cloud execution) with
`internal/command` as the driving adapter. JReleaser's `jreleaser-model-api` + per-service SDK
modules is close to ports with adapter modules.

**Fit for BaaS.** Good on the merits — 8 AWS services, invariants spanning several of them, and BaaS
already has proto-ports (`JobRecorder`, `JobSession.Instances`) that proved their value. Poor on
ceremony if applied uniformly: most AWS calls in BaaS are one-off and used by one command.
**Sketch.**
```
baas-model                            contract (keys, layout, vocabulary, item mappers)
baas-core   (new, no picocli, no SDK) pl.wsztajerowski.baas.core.{jobs,results,deployment,image}
                                      use cases + port interfaces: JobRecorder, Instances, Artifacts,
                                      StackGateway, ImagePointer, Identity, ...
baas-aws    (new)                     pl.wsztajerowski.baas.aws.{ec2,s3,dynamodb,cloudformation,imagebuilder,ssm,iam,sts}
                                      adapters implementing core ports; AwsClientFactory
baas-cli                              picocli commands + console; wires core to aws adapters
benchmark-runner                      ports already: ResultsStore, StorageService (keep)
```
**Migration cost.** High: two new modules, a port per interaction, all SDK fakes in tests rewritten
to port fakes. The value is real only for jobs and image/deployment; the rest is ceremony.

### 2.4 Command pattern + use case / interactor per command (handler / mediator)

**Core idea.** Each CLI verb maps to one request object and one handler (`RunJob` → `RunJobHandler`);
picocli commands build the request and dispatch, optionally through a mediator/bus. Pairs with CQRS
(commands vs queries).

**Layout.** `usecases/run/{RunJob, RunJobHandler}`, `usecases/query/{QueryResults, QueryResultsHandler}`,
`cli/*Command` that map options → request.

**Testing.** Handler tested directly with fakes; command tested only for option → request mapping.

**Strengths.** Kills the "logic in `call()`" problem directly; one obvious place per verb; request
records are immutable values that log and test well.
**Weaknesses.** The mediator adds indirection with nothing to mediate in a single-process CLI;
cross-command reuse (the stop step shared by Ctrl+C, poll cap and `jobs terminate`) does not belong
to any one handler and must live beside them anyway.
**Fits.** Many verbs with non-trivial logic; teams used to MediatR/Axon-style apps.
**Exemplars.** gh's `NewCmdX(f, runF)` + `xRun(opts *XOptions)` is this pattern without a bus:
cobra parses into an `Options` struct, and a plain `xRun` function does the work and is what the
tests call (with `runF` injectable to test parsing alone). Terraform's command → `backend.Operation`
is the same shape.

**Fit for BaaS.** Good, *without* the mediator. picocli already gives the command object; the gain
comes from moving the body into a handler that takes an options record and its collaborators.
**Sketch.** Within today's packages: `jobs/RunJob` (record of resolved options) + `jobs/JobLauncher`
(handler) called by `RunCommand.call()`; `deployment/Setup` + `deployment/SetupHandler`; etc.
**Migration cost.** Low–medium, command by command, no module changes.

### 2.5 Library-first: core library + thin CLI shell

**Core idea.** Everything a command does is a library call; the CLI is one consumer of it (others:
plugins, build-tool plugins, tests). The CLI layer only parses, resolves configuration, wires and
prints.

**Layout.** gh: `api/` (GitHub API client), `pkg/cmd/<noun>/<verb>/` (command + `Options` + run
function), `pkg/cmdutil.Factory` (lazily-built `HttpClient`, `IOStreams`, `Config`, `BaseRepo`),
`internal/` (config, git, prompts). kubectl: the `k8s.io/cli-runtime` staging module (flags →
`RESTClientGetter`, resource builders, printers) under `k8s.io/kubectl/pkg/cmd`, reused by plugins
via the same module. Terraform: `internal/command` (CLI) vs `internal/backend`, `internal/terraform`
(core graph engine). JReleaser: `jreleaser-model-api`, `core`, engine, per-service `sdks/*`, with the
CLI, Maven, Gradle and Ant plugins as thin shells over the same engine.

**Testing.** The library has its own unit/integration tests; CLI tests cover parsing, output and
wiring with fakes injected through the factory (gh: `httpmock` registry + `iostreams.Test()`;
"none of these things should ever happen for real when running tests").

**Strengths.** Proven at scale by every large CLI surveyed; forces orchestration out of the parser;
a second front end (CI action, Gradle plugin, service) is cheap; the factory is a deliberate,
small DI mechanism.
**Weaknesses.** Pays off most when there *is* a second consumer; otherwise it is a module split for
discipline's sake. Needs a rule about where config resolution lives (gh's `Factory.Config`).
**Fits.** Mid-to-large CLIs, multiple front ends, or a core that other tools embed.
**Exemplars.** gh, kubectl/cli-runtime, terraform, JReleaser, AWS CLI v2 (botocore as the library,
`clidriver` + `customizations/` as the shell).

**Fit for BaaS.** Good. BaaS already has the factory (`AwsClientFactory`) and a shared library
(`baas-model`). Its "second consumer" is real but narrow: `benchmark-runner` and the bash user-data
consume the contract, not the orchestration — so the library split that matters is the *contract*
split BaaS already has. Splitting orchestration into a `baas-core` module is optional; doing it by
package (enforced by a test) gives most of the value.
**Sketch.**
```
baas-model           contract (unchanged; add the user-data guard expression and status
                     vocabulary that bash consumes, so the third runtime reads the model, not the CLI)
baas-core   (optional module, or just packages)
                     pl.wsztajerowski.baas.{jobs,results,deployment,image,config}
                     no picocli imports; AWS SDK allowed
baas-cli             pl.wsztajerowski.baas.cli.{commands,commands.admin,console}
                     BaasApp, LoggingMixin, the factory
benchmark-runner     unchanged
```
**Migration cost.** Medium as packages (move bodies out of `RunCommand`/`SetupCommand`, split
`infra`); medium–high as a separate Maven module (POM, shading, test classpath for `CoreTemplateTest`
resources).

### 2.6 Plugin / extension architectures

**Core idea.** The core discovers and dispatches to externally supplied commands: executables on
`PATH` (`kubectl-foo`, `gh-foo`, `docker-foo` with a `docker-cli-plugin-metadata` handshake) or
in-process hooks (AWS CLI's botocore event emitter: `building-command-table`, `before-call`).

**Layout.** `plugins/manager` (discovery, versioning), a stable plugin SDK (kubectl's
`cli-runtime`, docker's `cli-plugins/plugin`), core commands themselves sometimes shipped as plugins.

**Testing.** Contract tests for the plugin protocol; plugins tested independently.
**Strengths.** Lets third parties extend without forking.
**Weaknesses.** A public, versioned contract to maintain; discovery and security questions.
**Fits.** Ecosystem tools with external contributors.
**Exemplars.** kubectl plugins / krew, `gh extension`, docker CLI plugins (`buildx`, `compose`), AWS
CLI customizations.

**Fit for BaaS.** Not as a code architecture. BaaS's one extension point — the operator's runner-image
extension (a raw AWSTOE document, stored verbatim, checked by the contract component) — is a *data*
extension and is already well-bounded. One maintainer, no third-party command authors.
**Sketch.** None recommended. **Migration cost.** High, for no user.

### 2.7 Vertical slices / feature modules

**Core idea.** Bogard: organise by feature, not by layer; each slice holds everything for one use
case (command, logic, data access) and slices share little. Minimise coupling *between* slices,
maximise cohesion *within*; abstract only where a slice needs it.

**Layout.** `jobs/run/*`, `jobs/list/*`, `results/query/*`, `deployment/setup/*`, plus a small
`shared/` (or `kernel/`) for what is genuinely common.

**Testing.** Per slice, whatever that slice needs — pure unit tests where it has rules, fakes where
it has I/O, LocalStack where it is mostly I/O.

**Strengths.** Change for one command touches one package; matches BaaS's noun-verb command tree
(`baas jobs run`, `results query`, `admin image build`); no mandated abstractions.
**Weaknesses.** Duplication across slices unless a shared kernel is curated; without a second rule
inside slices, each slice can become a small flat command-centric script.
**Fits.** Feature-rich apps where features change independently; small teams that dislike ceremony.
**Exemplars.** gh's `pkg/cmd/<noun>/<verb>/` tree is vertical slicing (each verb directory holds its
command, options, run function and tests) over a shared `api` + `cmdutil`. kubectl's
`pkg/cmd/<verb>/` likewise.

**Fit for BaaS.** Good. BaaS's packages already lean this way (`jobs`, `results`); `infra` is the
part that is layered. The noun list is fixed by CLAUDE.md's command tree, which gives the slice list
for free.
**Sketch.**
```
baas-model                        contract (unchanged)
baas-cli
  pl.wsztajerowski.baas           BaasApp, LoggingMixin, BaasVersion
  .console                        Console, Table, StatusLine, Watch, Hints
  .aws                            AwsClientFactory, OperatorSession, BucketProbe (cross-slice AWS plumbing only)
  .jobs        run, list, show, diff, download, terminate: commands + JobSession, JobStop, JobListing,
               JobRecorder, DynamoDbJobRecorder, Ec2 instances adapter, UserDataScriptBuilder, S3 upload
  .results     query: command + ResultsQueryService, Filters, Grouping, Table
  .deployment  setup, teardown: commands + CloudFormationService, DeployerPreflight, DeployerPolicyRenderer
  .image       build, show: commands + ImageBuilderService, RunnerImageRenderer/Parameters/Extension, SsmService
  .config      set, show, list, sync: commands + ConfigService, BaasConfig, DeploymentNames
benchmark-runner                  unchanged
```
**Migration cost.** Low–medium: package moves, `commands`/`infra` dissolved into slices. Mechanical
with an IDE; tests move with their classes.

### 2.8 Functional core, imperative shell

**Core idea.** Bernhardt (*Boundaries*, 2012): decisions live in pure functions over values; a thin
imperative shell fetches values, calls the core, and performs the effects it returns. Values, not
interfaces, are the boundary. Ports & adapters "at the level of functions".

**Layout.** No mandated packages; per feature, a `plan`/`decide` function returning a value (e.g. a
list of actions or a result record) and a shell that executes it.

**Testing.** The core needs no fakes at all — input value in, output value out; the shell gets few,
coarse integration tests.

**Strengths.** The cheapest testability there is; no mocks; good fit for Java 21 records + sealed
interfaces + pattern matching; scales down to a single function.
**Weaknesses.** Interleaved I/O-and-decide sequences (poll, react, poll) do not flatten into one
plan; forcing them yields "effect interpreters" that are more machinery than they save. Needs a
second style for the shell's organisation.
**Fits.** Anywhere, as a discipline inside another style; especially where rules are intricate and
I/O is simple.
**Exemplars.** Terraform's plan/apply split (a plan is a value computed before any change, applied by
a separate step) is the large-scale form; gh's run functions over `Options` structs are a mild form.
In BaaS: `ResultsFilters`, `ResultsGrouping`, `PackagesDiff`, `JobListing` (the `vanished` decision),
`DeploymentNameRule`, every renderer, `RunCommand.watchdogBound`.

**Fit for BaaS.** Very good as the rule *inside* slices. Many of BaaS's invariants are decisions
(which tags are reserved, what the watchdog bound is, whether a refused write means terminate, what
parameters setup submits on create vs update, which deployment absent `--deployment` selects) and
already have or could have pure homes. The stateful parts (`JobSession`'s poll, the shutdown hook,
image repoint-then-deregister) are inherently sequential; they keep narrow ports (as `JobSession`
does) rather than becoming plans.
**Sketch.** Not a package layout — a rule: each slice has pure deciders (records in, records out)
and a shell (the use case/handler) that calls AWS.
**Migration cost.** Low, incremental, test-led.

### 2.9 DI container vs manual wiring

**Core idea.** Who constructs commands and their collaborators. picocli's `IFactory` is the seam:
Micronaut (`PicocliRunner`, `MicronautFactory`) and Quarkus (command mode, CDI/ArC) inject beans into
commands; Spring Shell and `picocli-spring-boot-starter` do the same. Manual wiring: a composition
root and/or a lazy factory object passed to commands — gh's `cmdutil.Factory`, kubectl's
`cmdutil.Factory` over `RESTClientGetter`, docker's `command.Cli`.

**Testing.** Container: test-scoped bean replacement (`@MockBean`, `@Replaces`, Quarkus `@InjectMock`),
a container start per test class. Manual: pass a different factory or constructor arguments.

**Strengths (container).** Less hand wiring as graphs grow; configuration binding; native-image
support (Micronaut/Quarkus compile-time DI).
**Weaknesses (container).** A framework for a CLI whose graph is small; startup cost (Spring);
invisible construction — exactly the "invisible state that changes what a command hits" BaaS
CLAUDE.md forbids for deployment selection; a framework dependency the constraint set does not
include.
**Strengths (manual).** Explicit, debuggable, zero dependencies; laziness is a feature (BaaS's
`AwsClientFactory.deferred` means a command that fails before AWS makes no call).
**Fits.** Container: large graphs, existing framework shop, native-image target. Manual: almost every
CLI under ~50k lines; all four Go exemplars.

**Fit for BaaS.** Manual wiring, kept. Extend `AwsClientFactory` into a per-invocation context (config,
console, clock, client factory) and give commands a constructor or picocli `IFactory` that passes it.
**Migration cost.** None to stay; a container would be a high-cost move against the stated values.

## 3. Evaluation against BaaS's specific forces

| Force | What it rewards |
|---|---|
| Three runtimes sharing a contract (CLI, JVM runner, bash user-data) | A contract module with no orchestration in it — already `baas-model`; make the bash side read from it too |
| 8 AWS services, many invariants spanning two or three of them | Orchestration out of picocli classes; narrow ports *only* where a cross-service invariant is tested |
| ~11k-line CLI, one maintainer | Few modules, no framework, package-level rather than module-level boundaries where possible |
| "Simple; fail-safe edge cases; no extra mechanism" | No mediator, no container, no port-per-call; values and pure functions before interfaces |
| Tests today fake SDK client interfaces and use LocalStack | Keep that for adapters; move rule tests to pure functions so SDK fakes shrink |
| Command tree fixed as noun → verb | Slices by noun map 1:1 |

## 5. Recommendation

**Target: vertical slices by noun, each with a functional core and an imperative shell, over a
library-first contract — manual wiring.** Concretely:

1. **Modules stay three** (`baas-model`, `benchmark-runner`, `baas-cli`). `baas-model` remains the
   contract and gains what the bash runtime reads today from CLI classes (e.g. the job-status guard
   expression now exported from `DynamoDbJobRecorder.NOT_TERMINAL`), so all three runtimes depend on
   the model, not on each other.
2. **`baas-cli` packages become the nouns**: `jobs`, `results`, `deployment`, `image`, `config`, plus
   `console` and a small `aws` package for cross-slice plumbing (`AwsClientFactory`,
   `OperatorSession`, `BucketProbe`). `commands` and `infra` dissolve into the slices. This is gh's
   `pkg/cmd/<noun>/<verb>` with BaaS's fixed command tree as the slice list.
3. **Inside each slice, picocli classes only parse and print.** Each verb's body moves into a plain
   handler taking an options record and its collaborators (gh's `xRun(opts)`); `RunCommand.call()`
   and `SetupCommand.call()` shrink to option resolution + one handler call, which makes the
   currently untested success path testable.
4. **Decisions are pure functions over records** (functional core); **only cross-service sequences
   with an ordering invariant get a narrow port**, harvested from tests the way `JobRecorder` and
   `JobSession.Instances` were — e.g. image repoint-then-retire, teardown ordering. Everything else
   keeps calling its AWS service class directly and is tested with the existing SDK fakes/LocalStack.
5. **Wiring stays manual**: grow `AwsClientFactory` into a per-invocation context passed by the root
   command (or a tiny picocli `IFactory`), no container.
6. Enforce the boundaries with one ArchUnit-style test (or a plain classpath scan in JUnit): no
   picocli imports outside `*Command` classes; no `software.amazon.awssdk` imports in decider
   classes; no slice imports another slice's internals; `baas-model` imports nothing from `baas-cli`
   (already true by module).

Why: it fixes the two real defects (orchestration in picocli classes; the catch-all `infra`) with
package moves and extract-method work, adds no framework and no mandatory interface layer, keeps the
build's strongest boundary (`baas-model`) as the single shared contract across three runtimes, and
can be done one noun at a time.

**Runner-up 1: library-first with a separate `baas-core` Maven module.** Same slices, but the
orchestration lives in a module that has no picocli dependency, so the "commands only parse and
print" rule is enforced by the compiler instead of a test. Choose it if a second front end appears
(a GitHub Action in Java, a Gradle/Maven plugin, a service). Costs a module, shading and
test-resource plumbing now for a consumer that does not yet exist.

**Runner-up 2: hexagonal (ports & adapters), applied to `jobs` and `image`/`deployment` only.** The
strongest boundary and the best isolation of the cross-service invariants, which are where BaaS's
money-losing bugs live. Rejected as the overall target because a port per AWS interaction across all
slices is the "extra mechanism" the maintainer avoids; keep it as the escalation path for a slice
whose sequence tests become painful with SDK fakes.

Not recommended: plugins (no third-party command authors), DI container (invisible construction,
framework dependency, startup cost), mediator/bus (nothing to mediate in-process), full Clean
Architecture rings (module count and mapping ceremony out of proportion with ~11k lines).
